# Design: add-supervisor-composition

## Context

Upstream (balenaCloud) deploys supervisor v19 as a multi-container release through device target state. The supervisor identifies itself via hardcoded app UUIDs (`src/lib/supervisor-metadata.ts`) and the feature labels (`io.balena.features.*`) in its compose file are processed by the supervisor itself, injecting env/mounts into sibling services. None of that machinery exists for us: openBalena has no supervisor fleets, so the composition must be brought up by the OS.

## Key mechanisms (verified from source)

1. **Helios takeover** (`helios-legacy/src/takeover.rs` + `scripts/start.sh`): on start, helios looks for a container named `balena_supervisor` (created by meta-balena `start-balena-supervisor`), execs `node` inside it to write `apiEndpointOverride=http://127.0.0.1:48484` and `listenPortOverride=48480` into `/data/database.sqlite`, then restarts `balena-supervisor.service`. Idempotent.

2. **Supervisor re-bind** (`balena-supervisor/src/supervisor.ts:82`): with `listenPortOverride` set, the supervisor binds its API to `10.114.104.1:48480` (the `supervisor0` network gateway) instead of `0.0.0.0:48484`.

3. **`supervisor0` network** (`src/compose/network-manager.ts`): name `supervisor0`, bridge name `supervisor0`, subnet `10.114.104.0/25`, gateway `10.114.104.1`. The supervisor ensures it via a composition step during state apply — but only once a target state is applied. Our env script creates it idempotently at boot (identical config, so `supervisorNetworkReady()` accepts it) to avoid a post-takeover bind failure on fresh devices.

4. **Env normally injected by feature labels** (`src/compose/utils.ts:364-395`): we inject the equivalents manually:
   - `balena-api` → `BALENA_API_URL=$API_ENDPOINT`, `BALENA_API_KEY=$DEVICE_API_KEY` (from `balena-config-vars`)
   - `supervisor-api` → `BALENA_SUPERVISOR_HOST=10.114.104.1`, `BALENA_SUPERVISOR_PORT=$LISTEN_PORT` (default 48484), `BALENA_SUPERVISOR_API_KEY` = the supervisor's main key from its DB (`config` table, key `apiKey`; extracted with the same `node --input-type=module -e` + `sqlite3` trick helios itself uses)
   - `balena-socket` → bind-mount `/var/run/balena-engine.sock`, `DOCKER_HOST`
   - `dbus` → bind-mount `/run/dbus/system_bus_socket`, `DBUS_SYSTEM_BUS_ADDRESS=unix:path=/host/run/dbus/system_bus_socket` (helios needs this to restart `balena-supervisor.service` during takeover)

5. **Traffic flow after takeover**:
   - Supervisor (net=host) polls `http://127.0.0.1:48484` → relay (published port) → helios unix socket. Helios intercepts `/device/v3/<uuid>/state` (User-Agent `Supervisor/*`) and serves cached target state; other requests pass through to the API.
   - Helios dials the supervisor at `http://10.114.104.1:48480` over `supervisor0`.
   - User-container/dashboard API requests to 48484 hit the relay; helios answers `/v3/*` and `/v1/update` itself, forwards the rest to the supervisor.

## Decisions

- **`core` stays outside the composition.** The takeover requires the container name `balena_supervisor` and the meta-balena bootstrap already handles pull/update/restart semantics (`update-balena-supervisor`). Moving it into the compose would break both.
- **Compose binary (user choice)** over plain `balena run`: keeps the yml faithful to upstream's compose file, makes the service definitions declarative and diffable against upstream.
- **`docker-compose` standalone binary** (v5.5.0) rather than a cli-plugin: avoids patching the balena CLI fork; installed to `/usr/bin/docker-compose` with `DOCKER_HOST=unix:///var/run/balena-engine.sock` set in the unit.
- **`--env-file` interpolation** (`/run/supervisor-compose.env`, generated by `ExecStartPre`) rather than systemd `EnvironmentFile=`: keeps compose in charge of interpolation and fails loudly (`${VAR:?}`) when the env script didn't produce values.
- **`Type=oneshot` + `Restart=on-failure`**: the unit reconciles the composition at boot; container-level crashes are handled by `restart: always` inside the compose.
- **Helios version pinning** is a single global bitbake variable `HELIOS_VERSION` (authoritative pin in `conf/samples/local.conf.sample`, `?=` fallback in `meta-abrp/conf/layer.conf`), following the existing `SUPERVISOR_VERSION` convention. Both consumers render it at build time: `balena-supervisor.bbappend` seds `@HELIOS_VERSION@` into `supervisor-compose.yml` (do_install), and `docker-disk.bbappend` seds it into `entry.sh` in `do_compile:prepend` — the recipe's docker build (which COPYs entry.sh) runs in `do_compile`, and `do_patch`/`do_configure` are `noexec`; the prepend recopies the pristine file first so a stale rendered WORKDIR copy can't mask version changes.
- **Rollback caveat (important)**: disabling helios alone leaves the supervisor listening on `10.114.104.1:48480` and polling `127.0.0.1:48484` (dead). Full rollback is:
  1. `systemctl disable --now balena-supervisor-next.service` and `docker rm -f` the helios containers,
  2. clear the takeover keys:
     `balena exec balena_supervisor node --input-type=module -e 'import sqlite3 from "sqlite3"; const db = new sqlite3.Database("/data/database.sqlite"); db.run("DELETE FROM config WHERE key IN (\"apiEndpointOverride\", \"listenPortOverride\")");'`
  3. `systemctl restart balena-supervisor`.

## Risks

- Compose v5 CLI behavior verified locally with the exact binary; aarch64 checksum pinned from the release's `.sha256` asset.
- `docker compose down` leaves `supervisor0` untouched (declared `external: true`).
- If the supervisor regenerates its API key (e.g. `/v1/regenerate-api-key`), the env file is stale for that boot; next boot re-extracts it. Takeover itself is unaffected.

## Build-time sizing note

`do_image_size_check` (image-balena.bbclass) requires preloaded docker content + /boot to fit into the spare rootfs during HUP. Preloading helios (~62 MiB) plus the docker-compose binary on the rootfs (~46 MiB) exceeded the 320 MiB default rootfs free space on raspberrypi4-64 (CI 32236161266: 311296 KiB required vs 274432 KiB available). Fixed with `layers/meta-abrp/recipes-core/images/balena-image.bbappend` setting `IMAGE_ROOTFS_SIZE:raspberrypi4-64 = "${@balena_rootfs_size(d) + 98304}"` (+96 MiB, machine-scoped). Note: `IMAGE_ROOTFS_EXTRA_SPACE` is the wrong knob — `balena-image.bb` derives `IMAGE_ROOTFS_MAXSIZE = IMAGE_ROOTFS_SIZE` without the extra space, so `do_image_docker` rejects the grown rootfs (CI 32241360449). raspberrypi5 (640 MiB rootfs) passed unmodified.

## Control plane remote updates

### Problem

openBalena has no `/v6/supervisor_release`, so the OS-baked supervisor pin
never advances remotely, and helios was pinned at build time. Worse, the two
images form a pair (helios 0.25.28 ships with supervisor v19.0.8): updating
them independently risks takeover incompatibility. The requirement: push a
versioned *pair* to the fleet remotely, without reflashing and without
openBalena changes.

### Scheme: shared pair tag + labels (chosen)

CI (`build-controlplane.yml`) publishes both images under one version:

    controlplane-supervisor:v19.0.8-h0.25.28
    controlplane-helios:v19.0.8-h0.25.28

Both are `FROM <base>` + `LABEL io.abrp.controlplane.version=<pair>`
rebuilds: one config layer, zero new bytes (blobs are content-addressed and
shared with the base images; on-device pulls after the first are manifest
checks only).

Alternatives rejected:
- *Scratch bundle image with tarballs* — self-contained but doubles registry
  bytes and needs tar extraction plumbing on device.
- *OCI image index with annotated children* — no duplication but requires
  registry-API manifest walking (token auth, Accept headers) on device, and
  a plain `balena pull` of such an index is ambiguous.
- *openBalena supervisor_release endpoint* — would resurrect the balena-cloud
  push model but diverges the backend (Route A decision was: device-side).

### Device updater (`update-controlplane`)

- `--check` (timer, daily): pull both `:stable`, read labels. Labels
  disagree → skip (mid-push straddle, retries next tick). Pair equals
  `/mnt/state/controlplane-version` → no-op. Else apply.
- `<pair-tag>` (SSH): pull both pair tags, labels must match each other.
- Apply order: pull+verify everything first (zero interruption while
  downloading) → `update-balena-supervisor -i controlplane-supervisor:<pair>`
  (rewrites supervisor.conf on the state partition, restarts core) → write
  `HELIOS_IMAGE=controlplane-helios:<pair>` to the override → restart
  `balena-supervisor-next` → record version + `sync -f /mnt/state`.
- Restarting `balena-supervisor.service` stops `balena-supervisor-next`
  (systemd Requires= propagation); the updater always re-starts the next
  unit afterwards, including on the failure path.
- First tick after flashing: supervisor runs the *labelled* rebuild of the
  same bytes (different config digest), so expect exactly one core restart
  while references converge to the controlplane namespace. Subsequent
  no-op ticks restart nothing.

### Promotion / rollback

1. Dispatch build-controlplane (promote=false) → canary:
   `balena ssh <uuid> update-controlplane <pair>`.
2. Re-dispatch with promote=true → `:stable` moves → fleet converges within
   ~24h (OnUnitInactiveSec=1d, RandomizedDelaySec=3600).
3. Rollback: re-dispatch promote with the old pair (or SSH per device).
   Pair tags are the only rollback anchor — never delete them.
4. GHCR packages are created PRIVATE on first push; flip to public in the
   package settings or devices cannot pull anonymously.
